# Cloudflare IP

给走 Cloudflare 的域名挑一条更快的线路，并写进本机 `/etc/hosts`。

## 一句话原理

同一个 Cloudflare 域名，官方默认给你的那条线路可能很远（实测过落点在阿姆斯特丹、首字节 2.7 秒）。
本工具把 Cloudflare 的候选线路逐个测一遍，挑出对你最快、且**真的能服务你这个域名**的一条，写进系统解析表。

## 启动

```bash
./cloudflareip              # 预览模式：能测速看结果，不改动系统
sudo ./cloudflareip -write  # 允许写入 /etc/hosts
```

一次性程序：没有后台循环、没有定时重测、没有自动切换，你测完、应用完按 `Ctrl+C` 退出就结束了。
启动后会打印网页地址（默认 `http://127.0.0.1:17890/`），桌面环境下会自动打开浏览器。

配置自动创建在 `~/.config/cloudflareip/config.json`，运行状态在同一个目录的 `state.json`。

## 网页上有什么

页面按步骤展开：**先只有「添加域名」和「系统 hosts」** → 添加后出现该域名的测速入口 → 点了测速才出现候选表和历史。

每个域名自己一张卡片，卡片内包含它的当前节点／线路位置／打开速度／已写入条数，以及「重新测速」「应用优选」；具体某个 IP 用表里的「应用」。

- 候选最多展示 6 个（按该域名的页面级打开速度排序）。
- 「应用优选」= 把该域名排名前 3 的 IP 一起写进 hosts（主 + 2 备）。
- 表里某个 IP 的「应用」只写那一条。
- 测速进行中也能继续添加／删除域名，两者互不阻塞。
「还原默认」和每行的删除（×）都在「系统 hosts」卡片里，历史卡片的「清空历史」只清历史。

| 区块 | 说明 |
|---|---|
| 四个数字 | 当前节点、线路位置（机房城市）、打开速度 |
| 系统 hosts | 本机解析表原文；本工具写入的行可逐条删除（×），右上角「还原默认」整块清掉 |
| 每个域名一块 | 该域名**单独测出来**的候选（不同域名的可用集合和速度可以完全不同），由快到慢 |
| 要加速的域名 | 增删域名，改完立刻生效（不用重启） |
| 系统 hosts 文件 | 本机解析表原文，标出哪些行是本工具写的，以及**是否真的生效** |
| 过去的记录 | 每次测速/换线的历史 |

「是否生效」= 拿域名做一次真实解析，看结果是否等于我们写入的 IP。

## 原理

### 为什么会有「优选」这件事

Cloudflare 用的是 Anycast：几百个边缘机房对外是同一批 IP 段，任何一个边缘都能接手你的域名。
但你查自己的域名，官方 DNS 永远只回那两个记录（比如 `104.21.26.227` / `172.67.139.126`），
它给的是「离你最近的官方选择」，未必是「对你最快的那个」。

实测差距很大：默认分到阿姆斯特丹，首字节 2.7 秒；换一条洛杉矶的线路，0.3 秒。同一台机器、同一时刻。

### 第一个坑：能连上 ≠ 能服务你

随便拿一个 Cloudflare IP 去测速，它会响应，但可能返回：

```
403 error code: 1034
```

这叫 EDGE_RESTRICTED——**这个边缘不在你域名的可服务集合里**。
它算「有响应」，所以只看「通不通」的测速工具会把它排到第一名，然后你怎么用都用不了。
判定方法：用你自己的域名做 SNI 去请求，返回 200 且带 `colo=` 才算可用。

### 第二个坑：握手快 ≠ 页面快

`/cdn-cgi/trace` 只是边缘的一道极轻的接口，一个 RTT 就回。
真正打开页面还要 Worker 执行、回源、渲染，两者排名经常不一样
（实测初筛第一 `104.19.51.50`，复测完第一变成 `103.21.244.204`）。

### 所以流程是四步

```
候选池      从 Cloudflare 官方公布的 16 个网段里均匀抽样（默认每段 8 个 ≈ 127 个 IP）
   │
TCP 预筛    只做 443 三次握手（1 个 RTT，4 秒超时）；丢包链路上比完整 TLS 容易过
   │
可用性筛选  用「你的域名」做 SNI 请求 /cdn-cgi/trace
            200 + 有 colo 才算可用；403/1034、超时、证书错全部淘汰
            ← 这一步就产出「初筛」结果，网页上立刻能看到
   │
页面级复测  对通过者发真实页面请求，取多次中位 TTFB，按真实打开速度重排
            ← 复测完成，表格原地刷新
```

每个域名**分别跑一遍**：1034 是按 hostname + zone 判定的，同一批 IP 对不同域名可用性不同
（实测 `openlist` 8/47 最优 LAX、`www` 10/47 最优 SJC）。

### 落地与验证

- 只改 `/etc/hosts` 里带标记的那一段，块外一字不动；原子替换（临时文件 + rename）、写后读回校验、内容没变不落盘。
- 每个域名写前 3 名（主 + 2 备），多行同名是合法的，按顺序尝试。
- 「是否生效」不是猜的：拿域名做一次真实解析，比对 hosts 里写的 IP，不一致就标红。

## 配置项

配置在 `~/.config/cloudflareip/config.json`，首次启动自动生成。

| 键 | 默认 | 说明 |
|---|---|---|
| `domains` | `[]` | 要测的域名，可以在网页里增删 |
| `hosts_path` | `/etc/hosts` | 写入目标，测试时可指向副本 |
| `listen` | `127.0.0.1:17890` | 网页监听地址 |
| `candidates_per_range` | `8` | 每个网段抽几个候选（16 段，共约 127 个） |
| `conc` | `64` | 探测并发 |
| `timeout_s` | `5` | 单个 IP 的超时；链路抖动大就调大 |
| `top_n` | `6` | 候选表最多展示几个（上限 6） |
| `repeat` | `3` | 页面级复测每个 IP 测几次取中位 |

「应用优选」固定写前 3 名（主 + 2 备），不跟配置走。

## 它不做什么

- **不做守护**：没有后台循环、没有定时重测、没有自动切换。一次性程序，测完应用完就可以关。
- **不动别人的解析记录**：只维护 `/etc/hosts` 里自己标记之间的那一段。
- **不替你改代理配置**：域名走直连要你自己在 mihomo 里配好（见下一节），否则优选白做。

## 和 mihomo 的关系（本机实测）

如果本机在跑 mihomo 之类带 TUN + fake-ip 的代理内核，**光写 `/etc/hosts` 不一定有用**，
因为浏览器拿到的可能不是真实 IP。下面这三条是让优选真正生效的前提。

### 1. 这个域名必须走 DIRECT

```yaml
rules:
  - DOMAIN-SUFFIX,fnnas.bond,DIRECT     # 放靠前的位置
```

域名如果走代理，流量走的是代理出口，跟工具测的那条直连路径完全无关，优选数字等于白测。

### 2. DNS 要读系统 hosts

```yaml
dns:
  enhanced-mode: fake-ip
  fake-ip-range: 198.18.0.1/16
  use-hosts: true            # 启用下面的 hosts 表
  use-system-hosts: true     # 同时读取 /etc/hosts   ← 关键
```

`use-system-hosts: true` 是这条链路的命门。它的效果是：
**hosts 命中时直接返回真实 IP，不再返回 fake-ip**。本机实测：

| 查询 | 结果 | 说明 |
|---|---|---|
| `getent hosts cloudflare-dns.com` | `1.1.1.1` | 命中 hosts → 真实 IP |
| `getent hosts dns.alidns.com` | `223.5.5.5` | 命中 hosts → 真实 IP |
| `getent hosts openlist.fnnas.bond`（应用前） | `198.18.9.145` | 没有记录 → fake-ip |
| `getent hosts openlist.fnnas.bond`（应用后） | `104.16.227.142` | 命中 hosts → 钉住的真实 IP |

所以完整链路是：

```
浏览器访问域名
  → 系统 DNS（指向 mihomo）命中 /etc/hosts → 返回真实 IP，不再是 198.18.x
  → 连到那个 IP，规则匹配 DOMAIN-SUFFIX → DIRECT
  → 走你家宽直连，和测速时是同一条路
```

### 3. 让裸 IP 的探测走直连

```yaml
tun:
  auto-route: true     # 只接管 fake-ip 网段（默认行为，别改成接管全部）
```

`auto-route: true` 时 TUN 只接管 `198.18.0.0/16`，裸公网 IP 不进 TUN。
这就是为什么测速能反映真实家宽路径（实测 `ip route get 104.18.170.170` → `dev wlp1s0`，不是 TUN）。

### 三个会让优选失效的情况

| 情况 | 后果 |
|---|---|
| 把域名改成走代理 | 流量走代理出口，和测的那条路无关 |
| 关掉 `use-system-hosts` | hosts 不被采纳，浏览器又拿到 fake-ip |
| 给 Cloudflare 网段加 `IP-CIDR,...,代理` | 测速本身就被污染（测到的是节点→CF 的延迟） |

### 生效自检

```bash
getent hosts 你的域名
```

- 返回你钉的 IP（如 `104.16.227.142`）→ 优选真的生效了（本机实测就是这个结果）。
- 还返回 `198.18.x.x` → hosts 没被采纳，先查 `use-system-hosts`。

### 不想动系统 hosts 的话

也可以把结果写进 mihomo 自己的 `hosts:` 段（效果等价，但每次改都要 reload 配置）：

```yaml
hosts:
  "openlist.fnnas.bond":
    - 190.93.246.102
    - 104.18.170.170
```

## 边界

- 只对本机生效；手机等其他设备需要 DNS 层的方案。
- 单 IP 是单点，最坏有 1–3 分钟不可用窗口（靠守护兜）。
- 只优化「你 → Cloudflare 边缘」这一跳；网站本身慢、回源慢都不在其中。
- 本机若被代理软件接管解析（fake-ip），`/etc/hosts` 可能不被采纳，需在代理软件的 hosts 里同步一行。
